---

# Our Values

## Clarity over cleverness

Code should be obvious.

Future maintainers should understand the code without solving puzzles.

If clever code reduces readability, we choose readability.

---

## Maintainability over speed

The fastest code to write is rarely the cheapest to maintain.

We optimize for years, not hours.

---

## Security by design

Security is not a feature.

It is part of every feature.

Every input is validated.

Every output is intentional.

Every modification is recoverable.

---

## Safety first

Production data is valuable.

Before modifying production:

* Backup first.

* Verify.

* Make the change.

* Verify again.

* Create a post-operation backup.

Recovery must always be possible.

---

## Trust is earned

Users trust software that:

* behaves predictably

* explains itself

* documents itself

* protects their data

* fails safely

We build software worthy of that trust.

---

## Documentation is a feature

A feature is not complete until someone unfamiliar with the project can understand it.

Documentation should assume no prior knowledge.

Every major feature explains:

* What it does.

* Why it exists.

* How to use it.

* What success looks like.

* How to recover if something fails.

---

## Comments explain intent

Comments do not repeat code.

Comments explain decisions.

Future maintainers should understand *why* something exists.

---

## Tests protect the future

Every bug becomes a regression test.

Every feature receives tests.

Every release earns confidence through automation.

---

## Continuous improvement

Every commit should leave the project better than it was.

Reduce duplication.

Clarify documentation.

Improve comments.

Strengthen tests.

Simplify architecture.

Small improvements become excellence over time.

# Definition of Excellence

Code is not finished when it works.

Code is finished when:

* It is understandable.

* It is documented.

* It is tested.

* It is secure.

* It is maintainable.

* It is reviewed.

* It can be confidently changed years later.

# Legacy

Technology changes.

Good engineering does not.

Years from now, someone should be able to study this repository and immediately recognize that it was built deliberately, carefully, and with pride.

That is the standard we hold ourselves to.
