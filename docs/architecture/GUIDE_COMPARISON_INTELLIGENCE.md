# Guide comparison intelligence

`Compare-ChannelForgeXmltvGuides` is a deterministic, report-only comparison prototype. Its inputs are `ChannelForgeExternalEvidenceObservation/v1` objects created by `ConvertTo-ChannelForgeExternalEvidenceObservation`; XMLTV adapters and acquisition are outside this boundary. `Programme` and `GuideEvidenceRecord` are not neutral external-ingestion contracts.

## Scope and ownership

The caller supplies one playlist context, explicit evaluation time, optional expected-coverage windows, existing durable channel bindings, and previously accepted knowledge for comparison. The comparer owns candidate event correlations, ambiguity, freshness assessments, conflicts, coverage gaps, overlap findings, assignment anomalies, and historical-knowledge comparisons. It does not create or change durable bindings, confidence policy, accepted knowledge, XMLTV, playlists, or lineup state.

Only observations with an explicit `SourceScoped` or `Shared` binding context for the requested playlist can participate in comparison. `Shared` means explicitly shared by the observation contract; a source bound to a different playlist is out of scope. Unbound evidence remains in provenance and is reported, never assigned by inference. Existing durable channel bindings may map a source channel reference to a `ChannelId`; suspicious `ChannelAssignment` or `Network` fields are compared against that mapping and cannot retarget it.

## Correlation and findings

Same-channel guide comparisons use explicit source-record or provisional-subject hints when compatible, otherwise normalized title and participant evidence plus a bounded near-time interval. Their unique reciprocal-candidate rule and time-shift findings remain unchanged. A separate cross-channel assessment compares rows on distinct durably bound channels using normalized fuzzy titles, event corroboration, interval proximity, episode/subtitle agreement, and live/replay compatibility. Participant, episode, subtitle, or live-versus-replay contradictions block a candidate. Time matching uses normalized UTC instants while the report retains original display-clock values and offsets. A sorted interval sweep bounds pair examination to overlapping or near-time rows; it does not rescan every programme for every channel.

Cross-channel results carry a 0–100 confidence score, evidence basis, source/channel references, and observation provenance. Matching detailed descriptions can corroborate news and other programme rows; exact movie titles require matching category and close airtimes. One-to-many candidates are marked `NeedsReview`; no ordering winner is selected. Zone-less display clocks are excluded from cross-channel matching; offset-bearing source display values are retained beside normalized UTC. A uniquely corroborated fuzzy-title pair may produce a contextual alias proposal with channel/category/participant/episode/time scope, evidence references, confidence, version, and a reversible proposal status. Proposals remain `Proposed`, unaccepted, and `CanMerge = false`; this comparison report does not persist or apply aliases.

Channel evidence profiles are derived once from supplied durable bindings and observations, including bound channels with no observed XMLTV programmes. Profiles retain source freshness, canonical category keys (taxonomy aliases normalize to the registered key; unknown labels are omitted), explicit coverage windows, and coverage gaps. Missing-guide profiles request review across registered non-temporal OneGuide categories only when no programmes were observed; a programme row with an unknown category does not imply missing XMLTV. Gap candidates reuse supplied expected windows. `SourceAccess = NotEvaluated` and `CanFetch = false` are intentional: this report does not perform periodic scheduling, source research, or acquisition.

Findings include exact agreement, harmless metadata variation, title and participant conflicts, separate start/stop time conflicts, stale or future-dated observations, source-unavailable and rejected evidence, out-of-scope and unbound evidence, explicit-window coverage gaps, missing programmes only where another source has declared covering scope, benign duplicate overlaps, correlated time-shift overlaps, material overlaps, suspicious assignments, and conflicts with accepted historical knowledge. Missing coverage is never inferred without a supplied expected window. Source-data, observation, and fetch timestamps remain distinct; freshness uses source-data time when present and fetch time only as a fallback, relative to the caller's explicit evaluation time.

## Safety

The report is `REPORT_ONLY` and `ReadOnly`; it declares `CanPublish = false` and records no accepted-state or accepted-knowledge mutation. Every correlation, assignment assessment, and accepted-knowledge comparison is diagnostic evidence only. No finding automatically accepts evidence, modifies existing channel bindings, publishes XMLTV, or changes a lineup. The caller remains responsible for any separately authorized review or acceptance workflow.

Before serialization, every report string passes through a bounded safe projection that redacts detected URLs, credential-like values, local paths, contact addresses, and standalone 64-hex strings except generated observation/finding/correlation/alias IDs and artifact-fingerprint fields. JSON and returned report properties use that projection; Markdown is rendered from the same projection and escapes untrusted Markdown and HTML metacharacters. Matching uses the original evidence before this output-boundary sanitization.

Cross-channel candidates and contextual aliases never combine channel offerings, modify item identity, or change accepted authority. A separate knowledge store persists canonical ChannelIdentity records, source-scoped ChannelBinding records, and contextual ProgrammeAlias records through explicit plans and user confirmation. The comparer consumes approved/probationary/rejected aliases read-only; it does not approve, reject, revoke, or apply proposals.

## Durable contextual alias lifecycle

The knowledge store at `state/knowledge/learned.json` has its own versioned schema, canonical state hash, monotonic revision, append-only audit/history, exclusive writer lock, atomic replacement, and retained revision snapshots. The store is authoritative for identity and matching knowledge; it is not a source payload archive or part of `GenerationStore`.

`New-ChannelForgeKnowledgeChangePlan` creates hash-bound, revision-bound plans. `Apply-ChannelForgeKnowledgeChangePlan -ConfirmApply APPLY` is the only ordinary write path; stale plans fail closed. Explicit `IMPORT` and `RESTORE` operations validate snapshots and preserve monotonic local revisions. Rejected contextual aliases remain stored so the exact rejected context is not proposed again. Revocation is explicit; no operation merges channels or changes accepted lineup state.

Each contextual alias key covers both ordinal channel IDs and normalized title, subtitle, event status, categories, participants, episode number, competition, and exact UTC start/stop. Complete sanitized evidence-side records include the original observed values, bounded descriptions when available, source relationship/family/class, source reference, and source/observation/fetch times. These records are retained indefinitely by this store; referenced source XMLTV payloads are not retained or guaranteed available.
Knowledge-plan creation and snapshot import/restore reject URL-bearing, credential-shaped (including compound environment-variable names such as `API_TOKEN` and `AWS_SECRET_ACCESS_KEY`, plus Bearer/Basic authorization), contact-address, Windows/POSIX private-path, control-character, and overlength values in free-text fields before they can reach durable state, backups, or audit history. State validation also requires top-level alias sides and every evidence pair to support the exact stored context key.

`MarkProbationary` requires at least two distinct high-confidence evidence pairs (score ≥85), each with authoritative/independent non-mirror sides from distinct source IDs. Approved and probationary aliases only add bounded confidence after all original freshness, identity, interval, contradiction, strong-evidence, and score thresholds already pass. Alias evidence cannot independently establish a candidate.

## Scheduled report-only comparison

The scheduled comparer is disabled unless policy explicitly sets `GuideComparison.Enabled` and a safe explicit `PlaylistId`. It runs inside the existing bounded source-refresh child, consumes only already validated source-result rows and eligible fresh remote cache payloads, and makes no additional network request. Local XMLTV has unknown freshness unless the source supplies genuine time facts. The adapter uses a stable hashed EPG SourceId, redacts sensitive source names in its report, and resolves only a unique, active, approved exact `(PlaylistId, SourceId, raw SourceChannelReference)` binding. Unsafe or converter-trimmed raw-reference mismatches remain unresolved.
Both the public comparer and scheduled adapter enforce a fixed maximum of 256 input observations per run. Scheduled XMLTV parsing applies the remaining aggregate budget while streaming and rejects the next `<programme>` before materializing its programme or raw occurrence. Same-channel and cross-channel candidate pairs are each capped at 256; exceeding any limit fails closed rather than producing a partial comparison.

The stage writes an independently validated comparison report and an action-limited knowledge plan containing only `ProposeAlias` or `AppendAliasEvidence` operations. It never applies that plan, mutates accepted authority, or changes source results, caches, or last-known-good state. Comparison-stage failure is reported separately from source-refresh success.
If output redaction changes a proposal's context key, the adapter withholds that knowledge-plan action; it does not persist redacted sides under a mismatched identity.
